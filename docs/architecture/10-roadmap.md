# 10. Этапы, риски, открытые вопросы

## 10.1. Этапы внедрения

Порядок продиктован зависимостями: без организаций и договоров нет клиентов,
без сотрудников нет ни карт, ни выплат.

| Этап | Содержание | Результат |
|---|---|---|
| **0. Каркас** | Репозиторий, шаблон сервиса, CI/CD, k8s-окружения, Keycloak, наблюдаемость, базовый BFF | Работающий «hello world» через весь конвейер |
| **1. Фундамент** | `iam-svc`, `reference-svc`, `audit-svc`, `content-svc`, `notification-svc`, профиль и смена пароля, ролевая модель | Администратор может завести пользователей и справочники |
| **2. Организации** | `org-svc`: организации, холдинги, договоры, сканы, продукты, настройки WAY4 | Клиента можно завести в системе |
| **3. Сотрудники и файлы** | `employee-svc`, `file-svc` + шаблоны и валидация, журнал импорта | Загрузка реестров и ведение сотрудников |
| **4. Согласование** | `workflow-svc`, конфигурируемые маршруты, задачи согласующим | Заявки проходят проверку администратором |
| **5. Выпуск карт** | `cards-svc`, `integration-hub` (CRM, Factory, Карт Перс, WAY4), сага, построчные статусы | Первый сквозной бизнес-сценарий |
| **6. Выплаты** | `payment-svc`, интеграция с ДБО ЮРЛ, бесшовный переход | Второй сквозной сценарий |
| **7. Казначейство** | `treasury-svc`, `mail-worker`, EQ, суточные циклы, сверка | Ежедневный автоматический цикл |
| **8. Документы и выдача** | `document-svc`, шаблоны, задания на печать, выдача карт | Полный цикл до вручения карты |
| **9. Расчётные листы** | `payslip-svc`, API для ЛК | Внутрибанковский контур |
| **10. Кешбэк и автоперевыпуск** | Кампании кешбэка, предложения на перевыпуск | Завершение объёма ТЗ |

Этапы 5 и 6 — контрольные точки: после каждого система приносит пользу
самостоятельно, даже если дальнейшие этапы задержатся.

## 10.2. Риски

| Риск | Влияние | Что делаем |
|---|---|---|
| **Отсутствие идемпотентности на стороне WAY4** | Двойное зачисление средств | Проверить в первую очередь; при отсутствии — обязательный запрос статуса перед повтором, режим ручного подтверждения повторов |
| **Протоколы внешних систем не подтверждены** | Переделка адаптеров | Контракты фиксируются до этапа 5; адаптеры за интерфейсом, тип транспорта — деталь реализации |
| **Согласование ФИО при бесшовном переходе** | Отказы во входе легитимным пользователям | Ключ — ИНН физлица + ИНН компании; ФИО как контрольная сверка с нормализацией |
| **18 сервисов при среднем масштабе** | Издержки эксплуатации выше пользы | Поэтапная сборка в 9 деплой-групп (раздел 2.5), разделение по мере роста нагрузки |
| **Пиковая нагрузка в дни выплат** | Деградация в самый ответственный момент | Ёмкость по пику, KEDA по очередям, нагрузочное тестирование на профиле пикового дня |
| **Внешние системы — узкое место по RPS** | Реестр на 10 тыс. строк обрабатывается часами | Согласовать допустимый RPS с владельцами систем, батч-режимы, приоритетные очереди |
| **ПДн и требования регулятора** | Юридические риски | Раннее подключение ИБ и комплаенса, минимизация ПДн, шифрование, аудит |
| **Отсутствие тестовых контуров внешних систем** | Невозможно проверить интеграции до прода | Заглушки по контракту + обязательное требование тестовых контуров в план проекта |
| **Незакрытый казначейский цикл** | Ошибки в остатках корпоративных карт | Блокировка старта следующего цикла, алерт, ручной разбор |

## 10.3. Открытые вопросы

Требуют ответа заказчика. Отсортированы по влиянию на архитектуру.

### Блокирующие (нужны до старта соответствующего этапа)

1. **WAY4: поддерживается ли идемпотентность операций?** Есть ли ключ запроса,
   есть ли метод «запросить статус операции по ключу»? Без этого повтор при
   таймауте небезопасен. — *этап 5*
2. **Протоколы интеграций.** По каждой из семи систем: REST/SOAP/файловый
   обмен/хранимые процедуры, аутентификация, форматы, ограничения по RPS,
   наличие тестового контура. — *этапы 5–7*
3. **Бесшовный переход: механизм.** ДБО ЮРЛ и ОРИОН в одном Keycloak (OIDC)
   или подписанный одноразовый токен? Кто владеет ключами? — *этап 6*
4. **ЛК: чем идентифицируется сотрудник банка** при запросе расчётного листа —
   табельный номер, ИНН, идентификатор CRM? — *этап 9*
5. **Казначейство: формат письма от ДБО ЮРЛ.** Структура файла, где именно
   указана сумма (тема, тело, вложение), подписывается ли письмо, контрольное
   время поступления, действия при расхождении сумм. — *этап 7*

### Существенные (влияют на модель данных и процессы)

6. **Форматы загружаемых файлов.** ТЗ говорит «текстовые», но зарплатные реестры
   часто приходят в XLSX. Нужен ли Excel? Какие кодировки (UTF-8, CP1251)?
   Есть ли отраслевой формат, обязательный к поддержке?
7. **Принцип четырёх глаз.** Может ли автор заявки согласовать её сам при
   определённых ролях? Нужен ли порог суммы для второго согласующего?
8. **Лимиты на выплаты.** Есть ли лимит на заявку и суточный лимит на организацию?
   Кто их устанавливает?
9. **Глубина иерархии организаций.** Только родитель + дочерние (2 уровня) или
   возможны более глубокие холдинги?
10. **Сроки хранения** платёжных документов, расчётных листов, аудита, ПДн —
    что требует комплаенс банка?
11. **Кешбэк: как определяются получатели?** Сегменты, выгрузка из внешней
    системы, ручной список? Как рассчитывается сумма?
12. **Автоперевыпуск: критерии отбора.** Срок действия, износ, смена ФИО,
    инициатива банка? Обязателен ли акцепт клиента?
13. **Календарь рабочих дней:** один общий или отдельный на регион/организацию?
    Как обрабатывается заявка, поданная на нерабочий день, — отклоняется или
    переносится на ближайший рабочий?
14. **Удаление сотрудника.** ТЗ допускает «полное удаление» — но по сотруднику с
    историей выплат это конфликтует с требованиями хранения. Предлагается
    ограничить физическое удаление сотрудниками без денежных операций.

### Уточняющие

15. Требуется ли MFA для клиентского контура или только для административного?
16. Нужна ли поддержка нескольких валют, или только рубли?
17. Требуется ли электронная подпись заявок клиентом (УКЭП/ПЭП) или достаточно
    подтверждения в интерфейсе?
18. Нужны ли пользователям выгрузки отчётов (какие именно, в каких форматах)?
19. Мобильная версия клиентского интерфейса — нужна или достаточно адаптивной вёрстки?
20. Планируется ли миграция данных из действующей системы? Если да — объёмы,
    источники, требования к сверке.

## 10.4. Что нужно от заказчика для продолжения

1. Ответы на блокирующие вопросы (1–5).
2. Примеры реальных файлов: реестр на выпуск карт, реестр на выплаты, письмо
   казначейства от ДБО ЮРЛ, данные для расчётных листов.
3. Спецификации API внешних систем или контакты владельцев.
4. Перечень ролей и матрица прав в текущем процессе (кто и что согласует).
5. Профиль нагрузки: число организаций, сотрудников, реестров в месяц, размер
   типового и максимального реестра.
